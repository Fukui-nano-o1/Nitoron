# カタログ解説の執筆計画（クボタ全機種の9割）

作成日：2026-09-14 ／ 基点：main `e54939b`
決定（たきと）：3Dは提携後。今はカタログの説明を分野ごと・要素ごとに書き、取説の症状別索引を作る。クボタの9割以上を掲載してから提携交渉へ持ち込む。5機種ずつ進める。

## 守る規則（固定・3つ）

1. **原文と図を転載しない。** 数値・事実は使う。文章は自分の言葉。図は載せず、頁を指す。
2. **数値は必ず頁を添える。** 出典のない数値は書かない。「取説 印刷p.xx（PDF yy）」または「製品ページURL・確認日」。
3. **原典にない手順を書かない。** 停止・冷却・分解順序・締付値は原典の頁を指すだけ。自分で手順を作らない。

これに加えて、既存の規則：推定は推定と書く／未確認は未確認と書く／実修理の成功は別に数える。

## 執筆の型（1機種＝6要素）

要素：エンジン／走行／作業部／操作／安全／整備。各要素に、公称値＋頁、部品の役割（自分の言葉で1〜3文）、確認の入口（症状→点検箇所→原典頁）。安全と整備は原典頁の索引が中心で、手順は書かない。

## 進め方：5機種ずつ、最初の5で時間を計る

| 回 | 機種 | 目的 |
|---|---|---|
| 第1回 | TMS-200、TMS-300、TRS-300、TA-701N、KP-103 | 取説が取得済み（48／—／—／63／114頁）。**1機種あたりの執筆時間を計る** |
| 第2回以降 | 同じ分野を続けて歩行型25シリーズを先に埋める | 雛形と用語が共通で速い |
| その後 | 田植機→トラクタ→コンバイン→稲作関連 | 取説が厚く、要素の用語が変わる。1機種の時間を測り直す |

第1回の5機種が終わるまで、第2回の機種を決めない。5機種の平均時間×110 が総工数で、それが出て初めて期日を言える。

## 受入条件（1機種ごと）

- 頁の付いていない数値・文が0件
- 原文の写しが0件（一致検査：取説テキストと8語以上の連続一致がない）
- 手順の記述が0件（安全・整備は索引と条件の要約のみ）
- 全体諸元（長・幅・高・質量・エンジン型式）が製品ページと取説で一致、または不一致を明記
- 型式違い（W／M／PC等）を混同していない
- 開始・終了時刻と読んだ頁数を記録

## 自動化の範囲（今日確認）

取得系は動く：TMS-200（36秒）、TA-701N（49秒）、KP-103（43秒）で公式取説PDFを取得し、頁付きテキスト化できる。
自動抽出は信用しない：3機種とも諸元の自動読取は失敗か誤読（TA-701N は列がエンジン型式、KP-103 は質量1,240kgと誤読）。抽出器は資料の場所を探す道具にとどめ、数値は人が頁を見て転記する。

## 修理の入力（2026-09-14 追加）

決定（たきと）：修理を経営発表の項目（作物・面積・経営の数字・課題／仮説／実践…）に無理に入れない。修理は修理の内容入力を新しく作る。

実装：`meta.repair`（`src/repair-entry.mjs`）。構造は 機械（メーカー・型式・号機／年式・稼働時間）→ 症状（何が・いつから・起きる条件）→ 確認したこと（部位・見たこと／測ったこと・根拠の頁）→ 行ったこと（日付・内容・交換部品／品番・費用・時間）→ 結果（本人の申告：改善／変化なし／再確認していない／相談・確認した内容・次回の確認）。
- 入力は修理画面の「修理の内容」シート（`src/RepairEntry.jsx`）。空欄のまま保存でき、数値・日付の形式と「改善・変化なしは対処を書いてから」だけ検査する。
- 登録（3D）のない機械でも「登録のない機械の修理を記録する」から同じ入力で記録できる。型番から登録機種を推測して代用しない。
- 保存先は既存の記録（notes の meta ブロック／公開 snapshot）。修理以外の記録には `repair` を持たせない。旧修理記録の症状（issue）・案内からの追記（action／result）は「案内からの記録」として残す。
- 経営発表の入力画面（Editor）は変更していない。カタログ解説の記録は今も発表の項目に載っている。次に直す対象。
