# Codex修正案 v3：共通部品仮定を拡張し、領域ごとの予測を検証する

作成・確認日：2026-09-11。確認基点：`1c5f04973f1a2a268d415af71d15c240f1a983e3`。
担当：Codexが修正コードを作り、Claude Codeが同じ実ジョブで実現性・再現性・課題・仮説を検証する。

## 結論と今回の仮説

利用者が共有したClaude報告では、v2の分割修正は採用。PC752Nの全25点が領域へ所属し、形状対応7点は前面4点・背面3点となって別々に停止した。分割修正はここで終了する。

今回の仮説は1つ：**歩行型の共通部品仮定を増やすと、主要2領域で最低5点を満たし、各点を計算から外した場合にも位置の予測ができるか。** 数が増えたことやカメラ計算が完了したことだけでは採用しない。資料照合済み3Dは引き続き0部品、元の工程Aは未達である。

## 実装内容

- 既存14種類の大きさ・中心・名称判定は維持。明示実行のv3だけに8種類を追加し、計22種類とする。
- 新しい仮定はメインスイッチ、チョークレバー、燃料コック、燃料キャップ、ハンドル高さ調節レバー、副変速レバー、スタンド、ロープ掛けフック。完全な部品名と指定した表記ゆれだけを認識し、取付ボルト・配線・ブラケット・未分類レバーへ広げない。
- 機種名・型式・図上座標による分岐はない。8種類の寸法・取付位置は**Codexが設計したカテゴリ仮定**であり、メーカー資料や画像から抽出した値ではない。全て箱モデル。実形状、取付側、収納状態等は未確認。
- `prior-families.mjs`に名称、大きさ・中心の正規化値、取付に関する仮定、由来を記録。追加部品のJSONにも`priorDefinition`を残す。
- 原PNGへのv2領域付与は一度だけ行い、同じ複製を旧14種類と新22種類の両方へ渡す。最低5点、引出線の指し先のみ、所属不明では停止、別領域を混ぜない、という規則を維持する。
- 旧コマンド`experimental/run.mjs`は旧14種類のまま。新コマンド`experimental/run-priors.mjs`でだけv3を実行する。フロント、本体の型式入力パイプライン、DB、APIには接続しない。

## 予測力の見方

新しい部品中心を画像へ寄せれば、同じ点への残差は下がり得る。その数字だけでは評価しない。

各領域で1点ずつ除外し、残った点でカメラを再計算する。除外点の画像座標を学習に使わず、仮定した部品中心から位置を予測する。同じ訓練点の画像座標の平均を答えるだけの予測も計算し、**同じ除外点**で比較する。

- `cameraRmsePx`：カメラによるLOO予測のRMSE。
- `centroidRmsePx`：残りの点の平均位置によるLOO予測のRMSE。
- `cameraToCentroidRatio`：前者÷後者。1未満はこの単純な比較対象より誤差が小さいことだけを意味する。
- `relativeToCentroid`：`lower` / `not-lower` / `unavailable`。全除外計算が成立しなければ比較不能。平均位置の誤差が0の場合も比率を作らない。
- 元画像対角に加え、**対象領域の対角**で正規化した誤差も出す。ページの余白が大きいから小さく見える誤差と区別する。
- `cohorts.legacy`と`cohorts.added`で、元7点と新たな点の誤差を別集計する。追加点だけが平均を改善して、元の点への予測が悪い場合を見落とさない。
- `commonTargets`は旧・新の共通部品IDで比較する。旧4点・3点はカメラ未成立なので旧側の誤差はNULL。「v2の混合LOO1398pxから改善した」とは比較しない。
- 同一中心や同一ファミリの重複数も確認する。別IDの点が増えただけで、独立した位置根拠が増えたと扱わない。

このLOOは、共通仮定を前提とした**図上の条件付き予測**である。1枚の実データを繰り返し見た開発でもあり、別機種への一般化・奥行き・実3D精度の証明ではない。

## 表示と出力

新ビューアの青十字は、初期状態で「その点を除外した予測」。チェックを外すと従来の合わせ込み位置へ戻る。平均位置との誤差比較、領域対角比、比較不能も表示する。3Dに出す位置は従来の仮説候補のままなので、除外予測の青十字と一致する保証はない。

出力ディレクトリ：

- `experiment.json` / `viewer.html`：v3の結果と表示。
- `baseline/experiment.json` / `baseline/viewer.html`：同じ入力の旧14種類。
- `comparison.json`：領域別の点数、追加部品、両設定の状態、予測指標、8種類の仮定の定義。
- `regions.json` / `regions-1.svg`等：全点の同一領域分け。原本への書き込みなし。
- `run.json`：入力SHA、所要時間、API0回、実行時の機種固有入力0回。人による仮定の設計・レビュー時間は別扱い。

`exit 0`と`candidates-generated`は候補計算の完了であり、採用や工程A合格ではない。候補内のLOOが比較不能でもexit 0になる場合がある。点数不足等の正当な停止はexit 1でJSONを残す。出力先は新規ディレクトリに限定し、既存の原ジョブを上書きしない。

## Codexの検証範囲

Node v24.19.0、合成データのみ。

- 関連38件合格（v2の29件＋今回9件）。別の型式名を付けても配置が変わらないこと、旧既定で新ファミリが有効にならないこと、原入力不変を含む。
- 旧設定の既存合成出力は、修正前後で同一SHAを確認した。異なる実行環境間のビット単位の一致は要求しない。
- 合成ラスタ25点では旧4/3→新9/6。両方のカメラを計算。ただし9点側はLOO中に計算不能となり比較不能、6点側は平均位置に対する比率約0.991。これは仮定の妥当性を支持する実証ではなく、失敗も含む接続検証である。
- 同じ合成入力で3回実行し、`experiment.json`・`comparison.json`・`regions.json`・旧設定JSONのSHAが一致。原JSON・PNGのSHAは不変。
- カメラに整合する合成データでは予測誤差が小さくなる。無関係な座標を与える反例では、計算できても平均位置より悪いと記録する。
- ビューア生成と埋め込みJavaScript・ブラウザ検査スクリプトの構文を確認。
- **未確認**：実PC752Nの追加対応点数・予測誤差、v3の実ブラウザ、iPhone、既存132件を含む全回帰・ビルド。ここには今回報告の実ジョブのファイル実体がなく、Chromium実行ファイルもない。Claudeのv2実測をv3実測として転記しない。

## 判定条件を固定する

**接続の達成条件**：旧4/3の維持、主要2領域にそれぞれ有効な5点以上、領域別のカメラ計算、混合0、原本不変、3回一致、表示・回帰の合格。

**今回の仮説を支持する最低条件**：主要2領域とも全除外計算が成立し、カメラLOOが平均位置LOOより小さい（比率1未満）。さらに元から対応していた点の集計でもカメラ誤差が平均位置より小さい。明らかな名称誤対応・図の混合がないことを原図で確認する。これは必要な比較条件であり、機械としての正しさ・十分な絶対精度・他機種への一般化は保証しない。実データの結果を見てこの比較条件を緩めない。

接続だけ成立し予測条件が未達なら「接続は条件付き採用、配置仮定の妥当性は未支持」。条件を満たした場合も「次の独立検証へ進む候補」とする。**資料照合済み3Dは全ケース0部品を維持**。UIやテスト合格を元の工程A達成へ繰り上げない。

報告：実行SHA、原本SHA、領域別の新旧点数、独立中心数、全点/元の点のLOOと平均位置誤差、図・領域対角比、不能・除外理由、時間、外部API回数、機種固有介入回数。添付はcomparison.json、experiment.json、baseline/experiment.json、regions.json、領域SVG、run.json、両viewer.html、青十字切替画像、修正diff。

mainへの通常プッシュの既存許可は維持。検証済みの実験用変更だけを対象とし、主処理への接続、本番DB・実データ変更、強制プッシュ、新規課金は行わない。
